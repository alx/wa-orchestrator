wa-orchestrator 1 process · N groups

One WhatsApp account, registered groups, and a brain per group: a pi 1.2.0 agent run inside a sandboxed Docker container, with a locked LLM model.

Architecture

WhatsApp ──wwebjs──▶ index.js ──per group──▶ brain.js ──docker──▶ container (1 account) registry docker run pi agent ├─ /workspace = the group's own work dir ├─ /beads = beads repo (bd via BEADS_DIR) ├─ tools (git, hugo…) ├─ subagent (in-process child agents) ├─ herdr (host server over mounted socket) └─ 1 brain ≠ 1 group

The brain is chosen per group (the brain field of the registry), not per message nor per server. Two profiles ship by default:

profilefree-text pi …run modes
beads-projectproject beads (list/create by label)pi run <bead> → executes the bead, artifacts on branch task/<id>
site-projectscoped read-only beads (live Dolt DB, filtered to a set of epics)pi edit <instruction> → edits the site, verifies the build, commit + push

Quickstart

npm install
bash sandbox/build.sh          # docker image (pi, bd, jq, hugo_extended + pinned pi packages:
                               # provider, ask-questions, pi-subagents, pi-herdr + herdr client)
cp config.template.json config.json   # fill JIDs + absolute paths
cp brain-prompts.template.json brain-prompts.json   # adapt prompts
# user-scoped systemd units provided (fill <HOME>/<NODE_BIN>):
systemctl --user enable --now wa-orchestrator wa-orchestrator-dashboard

Prereqs: docker, xvfb-run, system Chromium, node ≥ 22. The WhatsApp session lives in sessions/ — one client per account, never two instances at once. Prompts load from brain-prompts.json (gitignored); without it the bot falls back to minimal generic built-in prompts.

Conversations (continuous memory per group)

Each registered group holds one continuous conversation, persisted as a pi session on the host — the bot is not stateless per message. The first turn of a conversation renders the full prompt (*.ask.first: identity, environment, hard rules); every later turn renders a slim continuation (*.ask.turn), because the session already holds the first-turn context. Run-mode calls (run/edit) land in the same group conversation, so a member can ask, order an edit, and check the result across messages.

  • Reset: send pi new in the group — the bot renames the group's session dir aside; the next message starts a fresh first turn.
  • Storage: <conversationDir>/<group-slug>/<created>_<slug>.jsonl per brain profile (one dir per group). Deleting it = amnesia; the bot keeps running.
  • Containers stay disposable (docker run --rm): continuity comes from the session file, and the model lock is re-verified on every start — resumed sessions included.

Clarifying questions (structured Q&A in the group)

When a requirement is blurry, the brain asks the group instead of guessing: the sandbox ships the pi-ask-questions extension (pinned, loaded via the local-path packages list in the host-generated settings.json), which registers an ask_questions tool. Over RPC it becomes a normal extension_ui_request/extension_ui_response dialog that brain.js bridges to the group:

  1. The brain calls ask_questions → pi emits a select (or input) request → the bot posts the question in the group with numbered options plus a “Type something.” row for free text.
  2. The next member message in that group is the answer — a number picks that exact option; free text takes the typed row (the follow-up input dialog is answered automatically, the group never sees it).
  3. The run timeout is paused while the group is being asked; no answer within questionTimeoutMs (default 30 min) → the dialog is cancelled and the brain continues.

Activity log: question_asked / question_answered / question_timeout entries.

Multi-agent primitives (delegation)

The sandbox bakes in two pinned delegation layers, so a brain is never stuck doing everything itself:

  • subagent tool (pi-subagents, in-process): the brain launches child agents — scout to find, reviewer to check, worker to build, oracle to consult, delegate for simple sub-tasks — in the same sandbox under the same constraints and model lock. Children are blocking by default (the one-shot RPC brain is SIGKILLed on settle, so a detached child would die mid-work); parallel children are allowed. Config is materialized per run: {"asyncByDefault": false, "toolActivation": "eager"} — eager, because the default "auto" mode hides the tool in any session with history.
  • herdr tools (pi-herdr, host panes): herdr_spawn_agent starts a visible agent pane on the operator's machine. The in-container herdr client talks to the host herdr server over a single bind-mounted socket (herdrSocketPath → HERDR_SOCKET_PATH); herdr_wait_output/herdr_get_agent_result harvest, herdr_message_agent steers, herdr_interrupt_agent stops. Panes are host-owned: they survive the disposable docker --rm brain runs, and a human watches or types in them from the herdr TUI. herdrSpawnPane pins a dedicated home pane (its own workspace) as the spawn target, so bot agents stay out of the operator's live work.

Host side (required for herdr children to actually start): the herdr.service user unit (template in the repo) keeps the herdr server running (starts only if none is running, Restart=on-failure, lingering); and pi-herdr is installed once on the host, self-contained:

mkdir -p ~/.local/share/wa-orchestrator/pi-herdr && cd $_
npm init -y && npm i @andrewjacop/pi-herdr@0.6.0

then set "herdrPkgDir" in config.json: brain.ts bind-mounts the dir onto itself and loads the package in-sandbox from the same absolute path (the child extension <pkg>/src/child.ts is injected into the child pi running in a host pane, so it must resolve there). Without herdrSocketPath/herdrPkgDir the herdr tools simply fail in-sandbox and the brain falls back to in-process subagents.

Extending

  • Add a group = one entry {"jid", "name", "brain"} in groups[] + a restart. JID: first message from the group, or xvfb-run -a node dist/discover.js during a maintenance window.
  • Add a brain = one profile in brains{} (beads repo, prompt entries, run modes) pointed at by the registry. Give it its own workspaceDir (one work area per group — never a shared project repo; the beads DB mounts separately at /beads, resolved from any cwd via BEADS_DIR).

Security

  • Every member of a registered group can command the bot (no per-member auth).
  • Write-capable run modes are scoped in the prompt: minimal edits, build before push, never force-push, never .github/.
  • Credentials are materialized inside the container, never in the repo (config.json and brain-prompts.json gitignored; only templates are published).
  • Everything is traced: activity/activity.jsonl + dashboard :8093.
